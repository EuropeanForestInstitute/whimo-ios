# Harvest Seasons — контракт API

> Historical contract: this August document is retained as project history. For the approved September client behavior and current public-contract findings, read the [new specification](../../.scratch/harvest-season-simple/spec.md) and [API findings](../../.scratch/harvest-season-simple/api-contract.md). In particular, its buyer/acceptance and automatic-consent rules are superseded.

Статус: черновик для командного ревью
Дата: 2026-08-19
Заменяет: `harvest-season-v2.md`, `harvest-season-v2.ru.md`

## 1. Назначение

Добавить учёт сезона сбора урожая в балансы commodity, транзакции и traceability.

This document described the proposed contract on 2026-08-19. Its original companion artifacts,
`openapi-v2.yaml` and `components-v2/`, are not present in this repository. It no longer establishes
current contract authority; use the September specification and public-source findings linked above.

Фича решает одну проблему: сейчас весь объём, которым владеет пользователь, находится в одном общем пуле,
поэтому одна покупка без traceability ухудшает traceability всего остального объёма пользователя. Сезоны
разделяют этот пул. Цепочка никогда не пересекает границу сезона, поэтому загрязнение также не может её
пересечь.

## 2. Зафиксированные решения

Изменения относительно предыдущего черновика, сформированные по итогам брейншторма 09.07, списка задач
от 14.07 и стендапа 19.08:

| Решение | Следствие |
|---|---|
| Одна транзакция относится ровно к одному сезону сбора урожая | `harvest_season_id` — скалярное поле, а не массив распределений |
| Сезон сбора урожая охватывает набор commodity | Сезоны могут пересекаться, если их наборы commodity не пересекаются; инварианты действуют отдельно для каждого commodity |
| Traceability вычисляется отдельно для каждого сезона | Входит в область работ; обход цепочки ограничен сезоном |
| Тестовые данные обрабатываются в отдельных окружениях | Нет тестового сезона, тестового флага и исключений из отчётности |
| Disposal отменён | Нет типа транзакции disposal и endpoint для disposal |
| Нет переноса между сезонами | Баланс остаётся в исходном сезоне, пока не будет продан |
| Транзакции могут создаваться в сезонах `past` и `archived` | Статус сезона носит описательный характер и не является ограничением |

## 3. Доменная модель

### 3.1 Сезон сбора урожая

Сезон сбора урожая определяет, когда был собран объём. Сезонами управляет backend: они создаются в
админ-панели и не имеют публичного API для изменения.

- Сезон охватывает набор commodity. Один сезон `2025/26` может одновременно содержать какао и кофе, а
  отдельный сезон `Coffee spring-summer 2025` — только кофе с другими датами.
- Сезон представляет собой полуоткрытый интервал дат: `start_date` включается в интервал, `end_date`
  не включается.
- Два сезона могут пересекаться по времени, только если их наборы commodity не пересекаются. Для одного
  конкретного commodity охватывающие его сезоны никогда не пересекаются.
- Статус принимает одно из значений: `active`, `past`, `archived`. Для одного конкретного commodity ровно
  один охватывающий его сезон имеет статус `active`.
- Статус носит описательный, а не разрешительный характер: пользователь может выполнять транзакции в любом
  сезоне, включая `past` и `archived`. Статус описывает текущее положение года сбора commodity и определяет
  значения по умолчанию на клиенте.
- API не возвращает отображаемое название. Клиент формирует название из двух дат. См. открытый вопрос 1.

### 3.2 Транзакция

Каждая транзакция содержит ровно один `harvest_season_id`, и этот сезон всегда охватывает commodity
транзакции.

Единственное исключение — ожидающая downstream-транзакция, созданная покупателем: покупатель не выбирает
сезон, поэтому поле имеет значение `null`, пока продавец не подтвердит транзакцию. Если запрос отклонён или
истёк без ответа, поле навсегда остаётся `null`.

Для продажи объёма из двух сезонов требуются две транзакции. Транзакции с частичным распределением между
сезонами не существует.

### 3.3 Баланс

Строка баланса представляет одну тройку `(user, commodity, harvest season)`. Один и тот же commodity
отображается по одному разу для каждого сезона, в котором пользователь владеет объёмом. Объём никогда не
перемещается между сезонами — нет переноса и disposal; объём покидает сезон только при продаже или конверсии.

### 3.4 Traceability

Traceability вычисляется внутри сезона. Обход цепочки и производный статус учитывают только транзакции того
же сезона сбора урожая, поэтому цепочка ограничена своим сезоном по построению.

История никогда не сбрасывается при смене сезона: объём, поступивший в сезон с плохим статусом traceability,
сохраняет его. Сезоны изолируют пулы, но не очищают их историю.

## 4. Ресурсы

### 4.1 `HarvestSeasonDTO`

| Поле | Тип | Обязательное | Значение |
|---|---|:--:|---|
| `id` | UUID | да | Канонический идентификатор, используемый в фильтрах и операциях изменения |
| `start_date` | date | да | Начало включительно |
| `end_date` | date | да | Конец, не включаемый в интервал |
| `status` | enum | да | `active` / `past` / `archived` |

```json
{
  "id": "223e4567-e89b-12d3-a456-426614174000",
  "start_date": "2025-09-01",
  "end_date": "2026-09-01",
  "status": "active"
}
```

Набор commodity намеренно не входит в payload: он может охватывать весь каталог, и ни одному клиентскому
экрану не требуется получать его полностью. Чтобы получить сезоны, подходящие для commodity, список нужно
отфильтровать по `commodity_id`.

### 4.2 `BalanceDTO`

Существующая структура с добавленным вложенным сезоном. `volume` всегда больше нуля.

```json
{
  "id": "9f2c1b04-6d3e-4f81-a0c7-5e2b9d41a6f3",
  "volume": 120.0,
  "commodity": {
    "id": "8b1f9c40-0a2e-4a5c-9f3d-2b7a1c6e5d40",
    "code": "1801",
    "name": "Cocoa beans, whole or broken, raw or roasted",
    "unit": "kg",
    "has_recipe": true,
    "group": {
      "id": "6a0d38f1-4c72-4b19-9a55-0f8e3d2c7b14",
      "name": "Cocoa"
    }
  },
  "harvest_season": {
    "id": "223e4567-e89b-12d3-a456-426614174000",
    "start_date": "2025-09-01",
    "end_date": "2026-09-01",
    "status": "active"
  },
  "has_recipe": true
}
```

### 4.3 `TransactionDTO`

Существующая структура с двумя дополнительными полями.

```json
{
  "harvest_season": {
    "id": "223e4567-e89b-12d3-a456-426614174000",
    "start_date": "2025-09-01",
    "end_date": "2026-09-01",
    "status": "active"
  },
  "allow_automatic_transaction": true
}
```

`harvest_season` имеет значение `null` только в ожидающей downstream-транзакции, созданной покупателем.

`is_automatic` сохраняет своё значение: транзакция *является* автоматической корректировкой баланса,
созданной backend. `allow_automatic_transaction` имеет другое значение: это сохранённое согласие продавца
на создание такой транзакции позднее, при подтверждении.

## 5. Эндпоинты

### 5.1 `GET /harvest-seasons/`

Пагинированный список, отсортированный по `start_date` по убыванию.

| Параметр | Тип | Значение |
|---|---|---|
| `commodity_id` | UUID, повторяемый | Ограничить результат сезонами, охватывающими **все** указанные commodity |
| `status` | enum | Ограничить результат статусом `active` / `past` / `archived` |
| `page`, `page_size` | int | Стандартная пагинация |

Количество сезонов не ограничивается контрактом. «Все сезоны» не является ресурсом: это клиентская опция,
представленная отсутствием `harvest_season_id` в запросе с фильтрацией.

Этот endpoint никогда не возвращает `409`. Ошибка конфигурации в админ-панели проявляется в операциях
изменения, которые от неё зависят, а не при получении списка.

### 5.2 `GET /commodities/balances/`

Основной Balance API. Больше не является deprecated.

- Плоский пагинированный список, один элемент на пару `(commodity, harvest season)`.
- Возвращаются только ненулевые балансы.
- Один и тот же commodity может встречаться несколько раз с разными сезонами.
- API никогда не суммирует объёмы разных сезонов.

| Параметр | Тип | Значение |
|---|---|---|
| `search` | string | Существующий поиск commodity |
| `commodity_group_id` | UUID | Существующий фильтр |
| `commodity_id` | UUID | Существующий фильтр |
| `harvest_season_id` | UUID | Ограничить результат одним сезоном; не передавать для всех сезонов |
| `orderings` | list | `commodity_name`, `amount`, каждое значение может иметь префикс `-` |

Поведение клиента, не контролируемое API: экран балансов по умолчанию показывает активный сезон и
предоставляет «Все сезоны» как явную опцию.

### 5.3 `GET /commodities/groups/`

Помечен deprecated в v2 и не должен использоваться экраном балансов. Значение `balance` остаётся агрегированным
по всем сезонам сбора урожая и сохраняется только для существующих клиентов.

### 5.4 `GET /transactions/`

Добавляется один необязательный фильтр.

| Параметр | Тип | Значение |
|---|---|---|
| `harvest_season_id` | UUID | Ограничить результат транзакциями указанного сезона |

Транзакция соответствует фильтру, когда её `harvest_season_id` равен запрошенному значению. Отсутствие
параметра возвращает всё, включая ожидающие созданные покупателем запросы, у которых пока нет сезона.

### 5.5 `POST /transactions/producer/`

Аутентифицированный пользователь является покупателем и получает объём.

```json
{
  "commodity_id": "8b1f9c40-0a2e-4a5c-9f3d-2b7a1c6e5d40",
  "volume": 100.0,
  "harvest_season_id": "223e4567-e89b-12d3-a456-426614174000"
}
```

Транспорт остаётся `multipart/form-data`; JSON выше описывает набор полей, а каждое поле сезона является
обычным полем формы, а не вложенной JSON-частью.

- `harvest_season_id` необязателен. Если параметр отсутствует, backend назначает сезон `active`,
  охватывающий commodity транзакции.
- Если параметр передан, сезон должен охватывать commodity транзакции, иначе возвращается `400`.
- Допускается любой статус, включая `past` и `archived`: регистрация старого урожая является допустимым
  сценарием.
- Если параметр отсутствует и ни один сезон `active` не охватывает commodity, запрос завершается с `409`.

### 5.6 `POST /transactions/downstream/`

**Созданная продавцом** (`action=selling`) — продавец выбирает сезон, из которого списывается объём:

```json
{
  "action": "selling",
  "commodity_id": "8b1f9c40-0a2e-4a5c-9f3d-2b7a1c6e5d40",
  "volume": 100.0,
  "harvest_season_id": "223e4567-e89b-12d3-a456-426614174000",
  "allow_automatic_transaction": true
}
```

- `harvest_season_id` обязателен и должен охватывать commodity транзакции.
- `allow_automatic_transaction` обязателен и должен быть явно передан как `true` или `false`.
- Значение `true` допустимо, только когда выбранный сезон имеет статус `active`, иначе возвращается `400`.
- Пока транзакция находится в статусе `pending`, объём не списывается и автоматическая транзакция не создаётся.

**Созданная покупателем** (`action=buying`) — покупатель указывает только commodity, объём и получателя:

- `harvest_season_id` и `allow_automatic_transaction` запрещены; если они переданы, возвращается `400`.
- Сезон указывает продавец-получатель при подтверждении.

Примечание по multipart: оба поля являются обычными полями формы, а не JSON-частью.

### 5.7 `PATCH /transactions/{transaction_id}/status/`

Существует три допустимые структуры запроса. Backend определяет ожидаемую структуру на основе сохранённой
транзакции и аутентифицированного участника.

| Сценарий | Тело запроса |
|---|---|
| Продавец подтверждает запрос, созданный покупателем | `status`, `harvest_season_id`, `allow_automatic_transaction` |
| Покупатель подтверждает транзакцию, созданную продавцом | Только `status` |
| Любой из участников отклоняет транзакцию | Только `status` |

```json
{
  "status": "accepted",
  "harvest_season_id": "223e4567-e89b-12d3-a456-426614174000",
  "allow_automatic_transaction": true
}
```

```json
{ "status": "accepted" }
```

```json
{ "status": "rejected" }
```

Передача полей сезона там, где они не ожидаются, возвращает `400`.

Ответ возвращает обновлённую транзакцию и автоматическую транзакцию, созданную при подтверждении, либо `null`,
если автоматическая транзакция не была создана:

```json
{
  "success": true,
  "message": "Transaction status updated",
  "data": {
    "transaction": {
      "id": "7c9e6679-7425-40de-944b-e07fc1f90ae7",
      "status": "accepted",
      "volume": 100.0,
      "traceability": "conditional",
      "harvest_season": {
        "id": "223e4567-e89b-12d3-a456-426614174000",
        "start_date": "2025-09-01",
        "end_date": "2026-09-01",
        "status": "active"
      },
      "allow_automatic_transaction": true,
      "is_automatic": false
    },
    "automatic_transaction": null
  }
}
```

Остальные поля `TransactionDTO` не показаны в примере только для краткости; объект представляет полный DTO.
`automatic_transaction` является полным `TransactionDTO` с `is_automatic: true`, если при подтверждении была
создана автоматическая транзакция.

Этот ответ заменяет ответ v1, содержащий только сообщение.

### 5.8 `POST /transactions/conversion/`

```json
{
  "recipe_id": "4c8a2f77-1de4-4a90-8b6c-3f5e9a01d2b8",
  "harvest_season_id": "223e4567-e89b-12d3-a456-426614174000",
  "input_overrides": [
    { "commodity_id": "8b1f9c40-0a2e-4a5c-9f3d-2b7a1c6e5d40", "quantity": 25.0 }
  ],
  "output_overrides": [
    { "commodity_id": "d41a7b62-9c08-4e35-b1f7-6a2c8e50d934", "quantity": 12.0 }
  ]
}
```

- `harvest_season_id` обязателен и должен охватывать каждый входной и выходной commodity рецепта. В противном
  случае запрос завершается с `400` и указывает первый commodity, который не охватывается сезоном.
- Клиент предварительно фильтрует подходящие сезоны, передавая commodity рецепта в повторяемом параметре
  `commodity_id` запроса `GET /harvest-seasons/`.
- Каждый вход списывается из этого сезона и должен иметь в нём достаточный баланс.
- Каждый выход зачисляется в тот же сезон, поэтому конверсия никогда не перемещает объём между сезонами.
- Конверсия никогда не создаёт автоматическую корректировку баланса.

### 5.9 `GET /transactions/{transaction_id}/traceability-counts/`

Структура ответа не изменяется, но меняется смысл: счётчики охватывают только цепочку сезона сбора урожая
этой транзакции. Новый параметр не добавляется — сезон берётся из самой транзакции.

### 5.10 CSV-экспорт

`GET /transactions/download/csv/` и `GET /transactions/{transaction_id}/download/csv/`.

- Одна строка на транзакцию, как и сейчас. Количество строк и семантика `X-Total-Transactions` не изменяются.
- Добавляются четыре столбца: идентификатор сезона, дата начала сезона, дата окончания сезона и статус сезона.
- Транзакция без сезона (ожидающая, созданная покупателем) экспортируется с пустыми значениями этих столбцов.
- Экспорт списка принимает `harvest_season_id` с тем же правилом соответствия, что и список транзакций.
- Экспорт цепочки по построению охватывает один сезон, поскольку сама цепочка ограничена сезоном.

GeoJSON и ZIP bundle не изменяются. Метаданные сезона в geodata-экспорте являются последующей доработкой.

## 6. Автоматическая корректировка баланса

Корректировка является явным побочным эффектом, возникающим при подтверждении. Она никогда не запускается
неявно.

1. Только продавец задаёт `allow_automatic_transaction` и всегда делает это явно.
2. Значение `true` допустимо, только когда выбранный сезон имеет статус `active`, иначе возвращается `400`.
3. Сезон `past` или `archived` никогда не может уйти в отрицательный баланс: недостаточный баланс возвращает
   `409` независимо от наличия согласия.
4. Когда объёма сезона `active` недостаточно и передано согласие `true`, при подтверждении создаётся одна
   автоматическая транзакция точно на недостающий объём в том же сезоне.
5. Когда объёма сезона `active` недостаточно и передано согласие `false`, подтверждение возвращает `409`.
6. Backend никогда не переносит нехватку в другой сезон. Продавец явно выбирает сезон.
7. Автоматическая транзакция не существует, пока исходная транзакция ожидает подтверждения, отклонена или
   осталась без ответа.
8. Балансы повторно проверяются при подтверждении. Модель резервирования отсутствует: неуспешное подтверждение
   оставляет транзакцию в статусе `pending` и ничего не изменяет.

## 7. Ограничение traceability сезоном

Изменяются два поведения, и оба следуют из одного правила: цепочка ограничена своим сезоном.

**Обход цепочки.** При движении вверх по цепочке от транзакции предыдущее звено сопоставляется по участникам
продавец/покупатель, commodity *и* сезону сбора урожая. Поэтому цепочка не может покинуть сезон, в котором она
началась.

**Вычисление статуса.** Traceability downstream-продажи определяется как худший статус среди принятых входящих
транзакций продавца *того же commodity и того же сезона*. Объём, купленный в `2025/26`, не может повлиять на
объём, проданный из `2026/27`.

Конверсия наследует то же правило: traceability выходов определяется как худший статус среди входов в рамках
сезона конверсии.

Следствие, которое важно явно сообщить клиенту: новый сезон начинается без входящей истории, поэтому статус
первых продаж из него определяется только покупками этого сезона. Плохая история не очищается, потому что сам
объём остаётся в сезоне, в котором был куплен.

## 8. Контракт ошибок

| Статус | Условия |
|---:|---|
| `400` | Отсутствующие или запрещённые поля сезона для участника и действия; сезон не охватывает commodity транзакции или каждый commodity рецепта конверсии; согласие на автоматическую транзакцию для неактивного сезона |
| `404` | Неизвестная транзакция, commodity, рецепт или `harvest_season_id` |
| `409` | Недостаточный баланс в выбранном сезоне; нехватка активного сезона без согласия; ни один активный сезон не охватывает commodity; несколько активных сезонов охватывают commodity |

Статус `422` не вводится. Доменные коды:

- `transactions.insufficient_harvest_season_balance`
- `harvest_seasons.active_not_configured`
- `harvest_seasons.multiple_active`
- `harvest_seasons.commodity_not_in_season`

Ошибки недостаточного баланса содержат безопасный машиночитаемый контекст:

```json
{
  "success": false,
  "message": "Insufficient balance for the selected harvest season",
  "code": "transactions.insufficient_harvest_season_balance",
  "errors": {
    "harvest_season_id": "223e4567-e89b-12d3-a456-426614174000",
    "available_volume": 60.0,
    "requested_volume": 100.0
  }
}
```

`harvest_seasons.commodity_not_in_season` содержит `harvest_season_id` и `commodity_id`.

## 9. Миграция

Все действия выполняются в указанном порядке до публикации v2.

**Сезоны.** Создаются через админ-панель. Покрытие должно быть непрерывным для каждого commodity: каждая дата
создания одной из legacy-транзакций commodity должна входить в сезон, охватывающий этот commodity. Текущее
согласованное правило — один сезон с 1 сентября по 31 августа, охватывающий весь каталог какао в каждой пилотной
стране; разделение по commodity или стране является последующим изменением.

**Балансы.** Каждая существующая строка баланса назначается сезону `active` своего commodity. Это приближение:
существующие запасы считаются запасами текущего сезона. Строки с нулевым объёмом удаляются.

**Транзакции.** Каждая цепочка помечается как единое целое: сезон выбирается по `created_at` корневой транзакции
цепочки и назначается каждой транзакции в этой цепочке. Назначение сезона каждой транзакции по её собственному
`created_at` разделило бы цепочки, пересекающие границу сезона, и обрезало бы их traceability, что противоречит
правилу ограничения цепочки сезоном, на котором построен этот контракт.

Это согласованное приближение. Оно не утверждает, что дата создания транзакции является фактической датой сбора
урожая. v2 никогда не должен возвращать legacy-транзакцию без сезона.

## 10. Не входит в область работ

- Тестовые данные. Обрабатываются в отдельных окружениях, а не в доменной модели.
- Транзакции disposal / write-off. Отменены.
- Перенос балансов между сезонами. Отменён.
- Публичные endpoints создания, изменения, архивирования и удаления сезонов. Только админ-панель.
- Фильтрация аналитики по сезонам; агрегированная аналитика продолжает суммировать все сезоны.
- Резервирование баланса для ожидающих транзакций.
- Метаданные сезона в GeoJSON и bundle-экспортах.
- Аутентификация, пользователи, уведомления и изменения geodata.
- Идентичность commodity в каталоге: commodity сохраняет один `commodity_id` во всех сезонах.
- Получение списка рецептов конверсии и схемы рецептов остаются независимыми от сезона.

## 11. Открытые вопросы

1. **Название сезона.** Контракт не возвращает название, поэтому клиент отображает сезон на основе двух дат.
   Это было однозначно, пока сезон представлял один глобальный период. Теперь, когда сезоны могут пересекаться
   по времени для разных наборов commodity, два элемента выпадающего списка могут выглядеть одинаково.
   Рекомендация: добавить задаваемое администратором поле `name` в `HarvestSeasonDTO` и позволить клиентам
   использовать его вместо вычисленного названия. Решение нужно принять до добавления в Swagger.
2. **Запрос на покупку из нескольких сезонов.** Покупатель запрашивает 100; у продавца есть 60 в одном сезоне
   и 40 в другом. При одном сезоне на транзакцию продавец не может удовлетворить запрос одним подтверждением.
   Нужно подтвердить, что продавец должен отклонить запрос, а покупатель — создать отдельные запросы для каждого
   сезона, либо определить сценарий частичного подтверждения.
3. **Назначение сезона legacy-цепочкам.** Назначение сезона на уровне цепочки корректно, но требует больше ресурсов,
   чем назначение на уровне строки. Нужно подтвердить, что это приемлемо для существующего объёма данных.
4. **Способ публикации.** Будет ли фича опубликована как `/api/v2` параллельно с замороженным v1 или как изменение
   существующего v1. Изменение структуры ответа `PATCH /transactions/{id}/status/` является ломающим в любом случае.
5. **Семантика статусов сезона.** Сейчас `past` и `archived` неразличимы для API. Если между ними должна быть
   разница, её необходимо описать; иначе один из статусов можно удалить.
